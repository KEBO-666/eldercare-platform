# 答辩问答预案（评委常见提问 × 标准回答）

> 使用方式：答辩前通读，重点记住「结论 + 理由 + 证据（文件/接口/测试）」三段式。
> 每个回答都对应代码位置，可现场打开源码或执行演示。

---

## 一、架构与选型

**Q1：为什么选 FastAPI，而不是 Django / Flask？**

A：三个理由。
1) **依赖注入**天然对应本系统的横切需求——认证、RBAC、数据范围、审计都是"每个接口都要过一遍"的通用逻辑，FastAPI 的 `Depends` 把 `require("elder:read")` 写成声明式一行，不会漏。
2) **自动 OpenAPI 文档**便于演示与验收，评委可现场在 `/docs` 调接口。
3) 分层更干净：Django 的 ORM/模板/Admin 强耦合，本项目的核心是算法（派单评分、预警规则、补贴分账），需要纯函数化才能单测与解释。
证据：`app/core/deps.py`（依赖链）、`app/api/v1/router.py`（模块化路由）、`app/algorithms/`（纯函数）。

**Q2：为什么演示用 SQLite，生产用 PostgreSQL？切换成本高吗？**

A：ORM 层（SQLAlchemy 2.0）完全屏蔽差异，切换只改一个环境变量 `DATABASE_URL`。演示用 SQLite 是零依赖、评委本地一键跑；生产用 PostgreSQL 是并发与事务需要。代价是 SQLite 不支持并发写，所以备份用 SQLite 官方 backup API 而不是复制文件（避免 WAL 不一致）。证据：`app/core/config.py` 的 `db_url` 派生、`docker/docker-compose.yml`。

**Q3：40 张表是不是过度设计？**

A：不是。赛题要求"档案—目录—预约—工单—健康—结算—权限审计"全链路，每一段都必须是可追溯的结构化数据。举例：如果省掉 `service_price_version`，就无法满足"历史工单按发生时点价格结算"；省掉 `alert_action`，预警的推送/升级/处置就不可审计。

## 二、核心算法

**Q4：派单评分为什么定 0.4 / 0.3 / 0.2 / 0.1？**

A：这是赛题给定的默认权重，我们做成**可配置**（`.env` 的 `DISPATCH_WEIGHTS`，也支持 `config_item` 运行期热改），并做了归一化处理：权重不要求和为 1，程序自动归一，避免配置错误导致分数越界。
四项的工程含义：
- 技能匹配 0.4 —— 能力不对，服务就是无效的，权重最高；
- 距离 0.3 —— 直接影响准时率和成本；
- 负荷 0.2 —— 防止单人过载导致服务质量下降；
- 评分 0.1 —— 质量参考，但评分样本少时有噪声，故权重最低。
证据：`app/algorithms/dispatch.py`（纯函数 + 单测）、`GET /api/v1/dispatch/{id}/candidates` 返回每人 `factors` 明细。

**Q5：怎么证明派单结果"可解释"？**

A：接口返回每名候选的四项因子原值（0~1 归一化）、权重、加权分与推荐理由文本；页面上用进度条可视化。评委可以现场修改权重（管理端配置），再次查询候选排序会变化——这就是可配置、可解释的证据。

**Q6：两个网格员同时给同一护理员派单，会重复派单吗？**

A：不会。派单在**同一事务**内完成：先做时段冲突检测（该护理员在 `scheduled_start ± 标准时长` 内无在途工单），再创建工单；并配合 `work_order` 上的状态约束与唯一性校验。生产环境 PostgreSQL 下可用 `SELECT ... FOR UPDATE` 行锁进一步加固。

**Q7：预警的误报怎么处理？**

A：三层机制：
1) **规则可配置**：阈值、连续次数、静默时长都在 `alert_rule` 表里，管理员可改可停用；
2) **冷却去重**：同老人同规则 30 分钟内只生成一条，避免刷屏；
3) **三态闭环**：处置结论必须为「已处置 / 误报 / 已转诊」之一，误报原因入库，误报率进入统计，用于反向调参。
证据：`app/algorithms/alert_rules.py`、`GET /api/v1/alerts/stats`。

**Q8：补贴分账的顺序是什么？上限怎么处理？**

A：先算政府补贴（`min(金额×比例, 月度上限-本月已用)`），再算长护险（`金额×长护险比例`），剩余为个人自付；三重保证 sum 等于工单金额，且 Decimal 四舍五入到分。补贴上限跨账单累计，避免"多张账单各自不超、加起来超"。
证据：`app/algorithms/subsidy.py`、`tests/unit/test_billing.py::test_subsidy_monthly_limit`。

## 三、安全与合规

**Q9：身份证号加密后，怎么按身份证查人？**

A：双列设计——`id_card_enc` 存 AES-256-GCM 密文（随机 nonce，无法等值比较），`id_card_hash` 存 HMAC-SHA256 摘要（同一明文恒定），检索时把输入做同样摘要再查索引。既保密又可精确匹配，且不可逆推明文。
证据：`app/core/security.py`、`app/models/elder.py`。

**Q10：数据范围控制真的生效吗？怎么证明？**

A：`apply_scope()` 统一在服务层拼接 SQL 条件，网格员只有 `grid_org_id == 自己网格` 的数据；跨网格访问返回 403 或空集。测试里专门构造两个网格各一位老人，用 grid2 账号查 grid1 老人断言 403/空。
证据：`app/core/deps.py::apply_scope`、`tests/integration/test_elders_api.py`。

**Q11：审计日志"不可篡改"怎么自证？**

A：哈希链——每条日志 `hash = SHA256(自身字段 + prev_hash)`。改动任意一条历史记录，后续所有 hash 都对不上，校验接口会返回断点 id。演示时可直接改一条记录再调用 `GET /admin/audit/verify`，`valid=false` 且定位到被改的那条。
证据：`app/core/audit.py`、`tests/unit/test_foundation.py::test_audit_chain_detects_tamper`。

**Q12：个人信息保护法要求的"最小必要、二次授权"体现在哪？**

A：默认所有接口返回脱敏值；查看完整信息必须 `POST /elders/{id}/grants` 提交理由，生成 10 分钟有效的授权记录，使用时校验归属/有效期/字段范围，并写 `used_at` 与审计。导出档案同样记录导出人、时间、条数。

## 四、工程与测试

**Q13：怎么保证状态流转不跳跃？**

A：五台状态机集中在 `app/core/state_machine.py`，表驱动；所有流转必须 `MACHINE.next(state, action)`，非法流转统一抛 409（`code=INVALID_TRANSITION`）。测试覆盖"未签到直接签退""已完成后再次签到"等非法跳转。

**Q14：定时任务（凌晨 2 点备份、每月 1 日结算）演示时看不到怎么办？**

A：任务函数与触发器解耦——`run_daily_backup()`、`run_monthly_billing()`、`run_alert_timeout_scan()` 都是普通函数，可被 APScheduler 定时调用，也可通过管理接口手动触发（`POST /admin/backup`、`POST /billing/generate`、`POST /alerts/scan`）。演示用"立即执行"按钮，效果与真实定时一致。

**Q15：测试覆盖了什么？**

A：单元测试覆盖算法纯函数与规则边界（取消 119/121 分钟、签到 199/201 米、血压 179/180、心率第 2/3 次、静默 47.9/48.1 小时、补贴上限截断、差异率 0.9%/1.1%、照片第 3/4 张）；接口测试覆盖 401/403/422/409；另有一组六条业务流程的端到端测试。运行 `pytest -q` 即可复现。

**Q16：多人并行开发怎么防止互相破坏？**

A：先冻结契约再并行——数据模型、状态机、权限点、路由表、测试夹具全部由一人先行冻结（`docs/CONTRACTS.md`），各模块按目录隔离并行开发，写入范围互不重叠，最后统一集成与回归。这既保证了质量，也说明团队具备工程化协作能力。

## 五、加分与展望

**Q17：适老化怎么做的？**

A：全局大字号（≥18px）、高对比配色、按钮最小点击区 44px、表格斑马纹、关键操作二次确认、错误提示口语化；老人/家属端只保留"预约、查看服务、评价、账单"四件事，减少认知负担。

**Q18：如果扩展到全市，系统需要改什么？**

A：组织树已经是街道/社区/网格三级自关联，扩展到区/市只需加层级；数据范围是配置项，不改代码；瓶颈在数据库与文件存储——把 SQLite 换成 PostgreSQL、附件对象存储、会话无状态化后可水平扩容；统计改为离线预聚合（定时物化视图）。

**Q19：这个系统上线前还缺什么？**

A：三条：短信/微信真实通道（当前为模拟写入 `data/logs/sms_sim.log`）、等保要求下的密钥托管（当前密钥在环境变量）、以及老年人隐私数据的生命周期治理（到期归档与销毁策略）。这些在文档"设计取舍"中已列明，是后续迭代方向。
