# 预约正常与异常反馈完善

日期：2026年11月12日。用户在预约时间冲突、周期预约和取消释放迭代后，继续提出：“正常与异常场景都有清楚反馈”。本文记录这次真实反馈引导的修改和验收，不替代完整聊天导出。

## 正常场景

| 场景 | 反馈与下一步 |
|---|---|
| 单次或四周时段检查 | 展示检查通过、次数与日期，明确“尚未创建或锁定，提交时重新检查” |
| 正在提交 | 清除先前绿色预检结果，锁定本次填写内容、显示等待，避免旧预检被当成提交成功 |
| 创建成功 | 常驻说明已创建一次/四次、等待受理、每次独立取消；本页不再重复提交，提供查看列表入口 |
| 受理、转待派单 | 常驻说明已确认的状态变更；对应行停止重复操作，提示查看列表取得最新状态 |
| 取消成功 | 显示实际取消金额、释放工单数、其余周期预约不受影响 |
| 爽约登记成功 | 明确爽约不计费，说明释放工单数 |

成功后不再自动跳转或刷新，避免导航失败覆盖已确认的操作事实。页面保留手动查看列表入口；打开列表时恢复成功提示。浏览器会话存储不可用，也不会改变已经确认的操作结果。

## 异常场景

| 场景 | 反馈与恢复方式 |
|---|---|
| 必填项或取消原因缺失 | 页内常驻提示，聚焦需要填写的控件，标记`aria-invalid`；填写内容保留 |
| 业务时间冲突、能力/范围不符 | 显示业务原因，周期冲突指出第几次，清除旧绿色状态；调整后可重新检查与提交 |
| 403无权限 | 中文解释账号权限限制，建议使用合适账号或联系网格员 |
| 404记录/项目不存在、409状态变化 | 提醒刷新列表核对最新状态 |
| 422参数不合要求 | 使用中文字段名说明要检查的内容，不展示原始JSON错误列表 |
| 429操作频繁 | 提醒等待，避免连续点击；写操作先核对列表结果 |
| 断网、超时、5xx、未知4xx | 写操作显示“结果尚未确认，服务器可能已处理”；暂停同次重复提交，提供列表核对入口 |
| HTTP200但返回HTML、空内容或缺失结果 | 不显示成功、不将取消费用猜成0元，作为结果待核对处理 |
| 登录过期 | 常驻登录说明和入口；新建表单按当前账号临时保存草稿30分钟，重新登录返回后恢复并重新核对 |

只有错误码与预期HTTP状态一致的已知应用业务拒绝，才能据接口契约说明本次没有创建预约；不能仅凭“4xx”得出这个结论。只读预检失败则可以明确说明没有创建预约。

预约请求增加15秒响应上限，覆盖等待响应及读取响应内容；超时中止浏览器请求不等于撤销服务器处理，因此仍按结果待核对处理。其他页面的API默认行为保持兼容，只有本轮预约调用显式启用超时。

写操作结果不明时，本页不会自动重发或把按钮恢复为可以立即再次提交。取消弹窗仍可关闭并查看列表，但本次操作按钮保持锁定，填写原因在弹窗关闭前保留。登录跳转后不承诺取消原因还能恢复；草稿恢复仅针对新建预约且按账号区分，草稿过期或恢复后即移除。

## 实际检查发现

- 先前预检成功绿色状态可能在提交冲突后残留，本轮已清除。
- 先前所有4xx均提示“未创建”，本轮改为核对已知错误码和对应状态。
- 先前断网/5xx取消文案“操作未完成”过强，本轮改为结果待核对。
- 先前200异常内容可能被误认为成功，本轮检查创建、预检、取消和受理所需的结果字段及对应预约ID。
- 先前请求无超时可能永久等待，本轮为预约请求显式增加超时。
- 先前必填、受理和转派单主要依赖短暂toast，本轮增加常驻说明与恢复入口。
