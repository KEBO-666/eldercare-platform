# 智能派单：候选排序、权重解释与无人可派处理

日期：2026年11月12日。用户在预约反馈完善后提出：“在智能派单完善候选排序、权重解释、无人可派时的处理”。本次记录真实后续开发与验收，不替代完整Prompt聊天导出。

## 操作方式

1. 网格员在预约页面受理预约，进入“智能派单”查看已受理或待派单预约。
2. 点击“查看候选”，查看本次实际生效的权重、筛选统计、排名和每项加权贡献。
3. 选择合格候选派单。服务器重新检查技能、服务半径、当日负荷与时间冲突；成功后显示工单号及查看工单入口。
4. 无人可派时，按筛除原因核对人员技能、位置、服务半径及排班，或与老人协商新的预约时间。点击重新计算可复查最新资源。
5. 仍需协调时填写原因，申请人工协调。系统记录日志、审计并向本网格员及绑定家属发送站内通知；预约保持原状态，不会自动安排人员或绕过硬约束。

## 候选排序与分数

先执行硬条件筛选，再计算四因子评分。只有在岗、满足必需技能、位置与服务半径有效、服务当日未达工单上限且时段无在途工单冲突的护理员才能进入推荐。

默认综合分为`100 × (技能×0.4 + 距离×0.3 + 负荷×0.2 + 评分×0.1)`。重点关注护理员在加权后再乘`0.8`。运行期`dispatch.weights`优先于环境默认；配置解析失败安全回退，页面说明实际来源。所有权重归一化为和为1。

| 因子 | 含义与边界 |
|---|---|
| 技能 | 必需技能全部具备才可入围；合格者得1，因此该权重对合格者提供相同贡献 |
| 距离 | `max(0, 1 - 直线距离/有效半径)`；有效半径取系统与本人服务半径较小值；不代表实际交通耗时 |
| 负荷 | `max(0, 1 - 服务当日工单数/每日上限)`；不含取消工单，使用预约服务日而非查看页面当天 |
| 评分 | 近30天评价均分/5；没有可用评价时采用明确标示的默认评分，不使用资源池缓存冒充本次评分 |

排序使用未舍入的最终总分，先按总分降序，再按实际距离升序、服务当日负荷升序、护理员ID升序。页面展示值可以四舍五入，显示同分时仍保留服务器排名，不在浏览器重新排序。默认返回配置的TopN；未展示的合格者不会被记为筛除。

原实现先把因素和总分舍入至四位再排序，接近分数可能碰撞；本轮保留精确因子与贡献，分数展示与排名计算分开。非法或非有限定位不再被计算为有效距离。

交叉检查还发现两处口径问题：极大权重数值相加溢出时，不能把内置回退结果冒称运行期配置正常生效；必需技能中的空串和首尾空格必须在推荐与最终派单时采用相同清理规则。本轮分别补充配置回退与技能规范化回归。

## 无人可派与接口失败

报告展示检查总人数、合格人数及首个失败原因的互斥计数：已尝试、停用、缺少技能、定位/半径异常、超出半径、当日满负荷、时段冲突。一个人只计入首个不满足条件的原因，所以合格人数加筛除人数等于检查总人数；该计数不代表每人只存在一个问题。

无人可派时显示原因和处理建议，提供重新计算、查看预约及人工协调申请。页面不再从全员资源池提供一个看似可绕过筛选的人工指派入口。候选接口断网、超时、损坏响应或权限失败时，明确说明推荐结果不可用，不冒称检查后无人可派，也不开放指派。

协调申请在提交时重新检查：若资源已恢复而出现合格候选，则拒绝旧的无人申请并提示重新计算。仍无人可派时，重复申请同一待派单阶段返回原记录，不重复发通知、不覆盖原原因。已受理转待派单属于同一阶段；实际派单后退回重新派单，才开启新的协调阶段。

派单与协调写操作等待时暂停按钮；成功结果持续显示。断网、超时、5xx或无法识别的成功响应不等于服务器未处理，页面提示先核对预约/工单结果并停止本页重复提交。推荐是只读检查，不占用护理员时段；最终派单仍重新验证。

## 验证与材料边界

本轮使用独立合成测试库与隔离浏览器，不修改实际运行数据库。环境依赖检查与Ruff通过；全量pytest **508项通过，零失败/错误/跳过，覆盖率89.35%（6895/7717行）**，JUnit记录耗时303.056秒。新增算法测试48项、推荐/协调集成测试22项均包含在全量结果中，不能再与508相加。

原生Node前端检查 **87项通过**（共享请求/预约61项、推荐数据验证26项），Edge **31项通过**。浏览器包含真实推荐、实际运行期权重、派单与工单详情、协调日志/通知/重复申请、资源恢复后的409复检，以及受控HTTP故障与手机滚动操作；故障注入不代表生产中发生过这些故障。
