# 派单页面解释与实际计算一致性

日期：2026年11月12日。用户在智能派单完善后追加“页面解释与实际计算一致”。本轮以真实计算输入、接口结果和页面展示逐项核对，修复可触发的口径差异。

## 已修复的不一致

| 问题 | 实际修复 |
|---|---|
| 预约须知固定写3公里、6单、Top3 | 使用与推荐接口相同的策略函数，展示实际环境半径、服务当日上限和限定1–20后的TopN |
| 种子/管理页使用`dispatch_weights`，算法只读取`dispatch.weights` | 兼容旧键；有效新键优先，再尝试旧键、环境与内置默认；返回实际来源键 |
| 两个权重键同时存在，修改旧键可能无效 | 保存任一键时同步已存在的另一键；同批冲突值拒绝，审计记录同步变更 |
| 系统配置接口返回环境权重，被误认为生效权重 | 返回算法相同解析器的归一化实际值；页面区分实际值、环境默认和存储项 |
| 默认评分配置超出范围或非法时，规则说明与算法采用值不同 | 通过同一评分函数安全解析与限制到0–5，元信息和候选使用同值 |
| 距离先舍入四位再显示两位，存在双重舍入 | 页面直接由原始距离显示两位，计算过程展示原始距离 |
| 贡献相加或同显示分可能让用户误解排名 | 主卡保留简表，另可展开原始因子、权重、贡献和最终公式；说明舍入与精确排序的区别 |

## 如何核对

点击智能派单的“查看候选”，每张候选卡可展开“原始数值与计算过程”。页面展示本次计算时间、预约服务日期和起止时段；当日负荷使用预约服务日，评价使用计算时刻之前最近30天。

每项贡献为`因子 × 本次实际归一化权重`。最终综合分为`四项贡献原值之和 × 重点关注系数 × 100`。重点关注系数来自后端算法常量，其余护理员系数为1。技能必须全部满足才可入围，因此合格者技能因子均为1。

原始展开区展示接口提供的浮点数值；简表保留有限小数位。原始浮点运算可能出现如`30.000000000000004`的尾差，不使用这些格式化后的数字重新计算或排序。页面也会校验原始输入与因子公式、因子与贡献、贡献和与总分、关注标记与系数、精确分数与排名；响应字段不一致时不开放本次候选派单。

派单权重支持保存后重新计算生效。半径、每日上限、TopN和默认评分仍从环境读取，需要调整环境并重启；系统配置页明确说明：仅保存这些同名配置项不会使派单算法热更新。页面顶部是打开页面时的快照，后续每次推荐以该次响应中的权重与时间为准。

## 验证

全量538项测试通过（无失败、错误或跳过），行覆盖率89.41%（6928/7749），耗时316.662秒；前端97项通过（预约公共反馈61项、派单36项），Ruff检查通过。真实API与Edge页面22项核对通过，最终浏览器记录位于`reports/dispatch-explanation-browser/20261112-193544/result.json`。浏览器验收使用独立合成数据库和真实API响应，保存两组权重下的`weights-A/B-report.json`与对应`dom.json`，逐项比较10张候选卡的因子输入、乘法贡献、加权和、系数、最终分及排名；不注入伪造的成功推荐结果。

重点场景包括：旧种子权重保存后生效、显式新键同步、重点关注降权、默认评分、真实近30天评价、未来服务日负荷与当天负荷区分、取消工单排除、同显示分保留精确排名，以及390px原始长数字换行。旧版本默认评分合同首次9项中7项失败、2项通过的日志保留，用于说明本次修复前的真实问题。

本轮原始API/DOM证据使用合成演示人员，不含真实数据库。它验证本次计算快照的一致性，不证明并发排班互斥、外部交通耗时或所有配置项均可热更新。PDF与视频仍为此前快照；本轮代码、文档与验收产物反映最新行为。本文记录真实用户后续需求，不替代完整原始对话。
