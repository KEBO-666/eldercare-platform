# 01 / 问题、用户与产品价值

社区居家养老服务跨越老人、家属、护理员、网格员和监管人员。预约需要核对时间、人员技能和服务范围，执行后又需要记录健康情况、质量与费用。信息分散容易造成重复沟通、调度冲突和异常遗漏。

颐邻将需求、人员、执行与健康预警连接为可追溯的业务链。当前为使用合成演示数据的全栈 MVP，尚未开展真实社区试点，不将演示结果等同于实际运营成效。

| 用户 | 核心目标 | 页面与操作 |
|---|---|---|
| 老人 / 家属 | 便捷预约、查看进展 | 本人预约、工单、账单、评价及预警进展 |
| 护理员 | 明确任务并记录执行 | 接单、签到、服务项、指标录入与签退 |
| 网格员 | 协调供需与处置风险 | 候选推荐、派单、人工协调和预警闭环 |
| 机构 / 街道 | 质量管理与监管 | 统计、投诉、结算复核及授权审计 |

派单是加权算法，健康预警是可配置规则；AI主要参与开发与排错，应用不调用大模型生成医疗建议。

# 02 / 一笔服务的数据闭环

老人或家属提交预约，系统核对时间、服务项目与本人范围。网格员受理并查看候选，先过滤不符合条件的护理员，再按实际因子排序；最终派单再次校验约束并生成价格快照。

护理员接单、定位签到、逐项完成服务、上传照片并签退。指标触发规则或人工异常上报后生成预警；有权限人员响应、记录进展、处置或转诊，并通过随访确认最终闭环。

| 阶段 | 关键记录 | 核对重点 |
|---|---|---|
| 预约 | 时间、老人、项目、周期 | 周期整组成功或回滚，取消释放占用 |
| 派单 | 筛除原因、候选、得分 | 公式解释一致，手工操作不绕过硬约束 |
| 执行 | 定位、项目、照片、小结 | 本人任务、合法状态、异常原因留痕 |
| 预警 | 响应、进展、处置、随访 | 权限、并发旧状态复检及最终闭环 |
| 结算 | 明细、金额快照、退费 | 可见范围、累计退费余额与审计 |

界面入口由实际权限过滤；服务端仍独立鉴权。隐藏按钮不能代替后端权限检查。

# 03 / 架构与 AI 的修改边界

后端采用 FastAPI 与 SQLAlchemy 2.0；前端采用 Jinja2、Bootstrap 与本地 ECharts；SQLite为主要验证数据库。保留现有技术栈降低重写风险，也使评审无需额外的前端构建服务或大模型密钥。

| 层次 | 代码位置 | 职责 |
|---|---|---|
| 页面与交互 | app/templates、app/static | 角色导航、表单、图表与可见反馈 |
| API与认证 | app/api/v1、app/core | 输入校验、认证、权限和数据范围 |
| 业务服务 | app/services | 事务、状态、跨实体规则与审计 |
| 算法 | app/algorithms | 派单评分、规则判定与补贴计算 |
| 模型与任务 | app/models、app/tasks | 持久化、调度入口与任务函数 |

给AI的约束是复用已有分层，不在模板里复制金额或评分算法，不通过ID绕过数据权限，不把合法状态流转改为任意字符串更新。算法应能独立测试，服务层负责事务和跨实体操作。

每次修改先定位现有实现和失败，再限定文件范围、执行回归、记录版本。代码生成完成不等于业务验收完成。

# 04 / 数据、状态与事务

核心实体包含组织、用户、老人、护理员、服务项目、价格版本、预约、工单、健康指标、预警、投诉、评价与账单。预约连接老人和服务项目；工单固定单价与价格版本，后续调价不重算历史服务。

| 单据 | 主线状态 | 设计重点 |
|---|---|---|
| 预约 | 待受理→已受理→待派单→已派单→服务中→完成 | 取消、爽约与重新派单有合法入口 |
| 工单 | 待接单→已接单→服务中→待评价→完成 | 异常、执行人、定位与上传范围 |
| 预警 | 待响应→已响应→处理中→待随访→闭环 | 生命周期由底层状态与流水共同派生 |
| 账单 | 草稿→待复核→已确认→已缴费或红冲 | 金额快照、差异复核与退费上限 |

周期预约逐次校验并整组提交；其中一周冲突就回滚本组。取消释放关联工单占用的时段。响应、处置、随访的状态与流水、通知、审计在同一事务中完成。

健康指标先保存，预警评估再单独提交。评估失败时保留已保存指标并明确反馈，不能引导用户重复录入指标。

# 05 / 预约：冲突、周期与结果确认

预约服务校验老人时间、必需技能、能力与服务项目；普通预约和周期预约采用同一业务约束。预检只提供当前条件的检查结果，提交时仍重新验证，避免预检成功被误解为已占用时段。

周期预约支持连续四周，并展示每次日期。任何一周冲突时整组回滚，不留下部分成功的记录。取消成功同步释放关联的排班占用，保留业务状态和审计。

用户后续要求“正常与异常场景都有清楚反馈”。因此修正预检绿色成功状态残留、异常响应误报成功、取消结果文案不确定等问题，并补充常驻反馈和恢复入口。

| 场景 | 页面反馈 | 后续操作 |
|---|---|---|
| 已确认成功 | 显示预约次数或取消结果 | 查看新记录或返回列表 |
| 明确校验失败 | 标明冲突或字段原因 | 保留输入，修改后重试 |
| 网络超时 / 响应不确定 | 提示服务器结果尚未确认 | 先核对记录，停止重复写入 |

实现及验证入口：预约功能迭代.md、预约反馈完善.md；完整对话证据由三条完整AI迭代证据链.md导航。

# 06 / 派单：排名与解释用同一计算

系统先筛选在岗、技能、有效定位、服务半径、日单量和工单冲突。未满足硬条件的人员不进入评分；手工派单仍重新检查同样条件。

默认综合分：100 × (技能×0.4 + 距离×0.3 + 负荷×0.2 + 评分×0.1)。重点关注护理员在加权后再乘0.8。运行期配置优先，页面解释实际来源，权重归一化后使用；无效配置回退并标明。

| 因子 | 实际口径 | 展示方式 |
|---|---|---|
| 技能 | 必需技能全具备才合格，合格者取1 | 因子、权重与加权贡献 |
| 距离 | 直线距离相对有效半径 | 不宣称实际交通耗时 |
| 负荷 | 服务当日有效工单 / 每日上限 | 不使用查看页面当天负荷 |
| 评分 | 近30天评价 / 5，缺失用默认值 | 明确默认值和取值边界 |

排名使用未舍入总分，依次按距离、负荷、ID打破同分；页面展示值允许四舍五入，但不重新排序。后端JSON与页面DOM交叉核对，修复旧配置键未生效和硬编码说明。

# 07 / 无人可派与人工协调

无人可派时显示检查总人数、合格人数及首个失败原因的互斥统计。一个人计入首个不满足的原因，合格人数与筛除人数相加等于检查总人数；未进入TopN展示的合格者不算筛除。

页面提供重新计算、查看预约和人工协调申请。协调记录包含原因、日志、审计与站内通知，预约保持原状态，不自动安排人员或绕过硬约束。资源恢复后旧的“无人可派”申请应被重新检查并拒绝。

推荐接口超时或损坏响应要说明“推荐不可用”，不能冒称“检查后无人可派”。写操作结果不确定时保留输入并先核对预约或工单，避免重复派单。

30分钟未接单从工单实际派出时刻计算，尝试尚未尝试且当前仍符合约束的人员；没有候选则提示人工协调。函数测试不等于生产调度器实际到点运行已全面验收。

实现与公式验证入口：智能派单完善.md、派单解释一致性.md；浏览器报告保留实际权重、JSON与DOM结果。

# 08 / 健康预警：响应到最终闭环

健康指标通过录入或模拟上报进入系统，支持阈值、连续异常和静默超时规则；同老人同规则有冷却去重。人工异常上报与规则维护使用不同权限。

| 生命周期 | 含义 | 合法后续操作 |
|---|---|---|
| 待响应 | 尚未首次确认 | 响应、进展或直接处置 |
| 已响应 | 首次响应完成，尚无处置结论 | 进展或处置 |
| 处理中 | 已有进展记录 | 继续记录或处置 |
| 待随访 | 已登记转诊，尚无最终结果 | 随访，实际确认后闭环 |
| 已闭环 | 已处置、误报核实或随访结束 | 仅查看，不重新打开 |

首次响应幂等，重复提交不覆盖首次时间或重复审计。直接处置先补记响应，确保时间顺序。转诊登记不是最终闭环，页面统计使用生命周期字段，闭环时间采用closed_at。

写入前复检数据库最新状态，避免旧SQLAlchemy会话覆盖别人已完成的处置。无权限或非法转换不得留下业务副作用；完整措施、前后状态、操作者与请求来源可按预警编号追溯。

# 09 / 权限、隐私与金额正确性

系统区分动作权限与数据范围。默认老人绑定本人，护理员限定本人工单关联老人，网格员按网格，机构按所属社区；没有绑定或范围时默认不获得广泛可见性。街道和超级管理员沿用现有范围约定，未新增多街道租户隔离。

健康读取不自动授予预警读取、处置、规则维护或管理员审计。导航、首页和详情链接独立按实际权限过滤；直接页面和API仍再次鉴权。

首页账单卡片与账单页使用相同的可见老人和明细汇总。老人只看本人金额，网格员只看范围内金额；护理员没有账单读取权限，不查询或展示账单卡片。

身份证、电话和地址加密存储并默认脱敏；明文查看需有理由的短期二次授权和审计。照片限制大小、像素与范围并清理元数据；CSV/XLSX文本防公式注入。

金额采用Decimal和价格快照，累计退费不得突破原明细及各付款方剩余额度。审计哈希链可以检测变化，但没有外部可信锚，不宣称绝对不可篡改。

# 10 / 多角色 UI 的推荐组合

按用户选定方案优化现有导航、卡片、按钮与配色，保留真实数据、信息架构和前端框架。主题由服务端登录角色决定，URL参数不能改变身份、权限或主题。

| 身份 | 背景 / 主色 | 使用重点 |
|---|---|---|
| 老人 / 家属 | 米白 #f6f5f0 / 浅绿 #3e6650 | 大字号、50px起步按钮和清楚反馈 |
| 护理员 | 浅青 #f1f6f6 / 青绿 #087e79 | 任务优先，主次操作清楚 |
| 网格 / 机构 | 蓝灰 #f3f5fa / 蓝色 #3c59c5 | 列表、协同和管理操作 |
| 街道 / 超管 | 深蓝 #0d1523 / 浅蓝 #88b6ff | 统计监管，文字与状态独立校准 |

共享语义变量控制卡片、表单、分页、提示、弹窗、Toast和图表；预警等级继续使用状态色加文字。标准按钮至少44px，支持三档字号、减少动态效果和浅色打印。

移动导航具备遮罩、Escape、Tab焦点循环和焦点恢复；关闭状态不可聚焦，无JavaScript时保留普通导航。图表独立缩放，圆环内部百分比与滚动图例避免窄卡片裁切。

# 12 / AI 意图控制与并行协作

参赛人确定业务目标、要求与后续修正；AI承担读码、方案、补丁、验证和材料整理。用户明确要求确认环境后多subagent并行执行，由主代理限定分工并整合。

| 控制环节 | 实际方法 | 可核对证据 |
|---|---|---|
| 目标 | 预约、派单、预警各有明确要求 | 用户原文与后续反馈 |
| 上下文 | 现有分层、代码、错误输出 | 工具调用和真实失败记录 |
| 约束 | 不重写框架、不改实际库、不伪造历史 | 隔离路径、补丁和版本映射 |
| 分工 | 复现、浏览器、证据、集成独占文件 | 真实任务与共享工作区记录 |
| 反馈 | 计算解释一致、异常反馈、权限状态追溯 | 第二轮用户指导与针对性修正 |
| 验收 | 单元、接口、浏览器与材料检查 | 原始报告、哈希和提交 |

不把子代理委派当作独立用户Prompt，也不把内部压缩摘要当作原始对话。不同模型不保证同Prompt生成相同代码，复现依据是版本、依赖与实际验证步骤。

# 15 / 十分钟运行与复现指南

前提：Windows、有效Python（已验证3.12.14）、Git与可用网络。主要路线为SQLite，不依赖Docker、外部数据库或大模型密钥。README含依赖清单、.env.example、演示账号与故障处理。

```powershell
git clone https://github.com/KEBO-666/eldercare-platform.git
cd eldercare-platform
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_dev.ps1
# 默认Python失效时附加：-BasePython '有效python.exe路径'
```
