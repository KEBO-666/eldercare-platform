# 01 / 问题、用户与产品价值

社区居家养老服务跨越老人、家属、护理员和网格员。预约通常需要核对时间、服务能力和人员技能，执行后又需要记录健康情况、评价与费用。信息分散会造成重复沟通、调度冲突及异常处理遗漏。

颐邻将需求、人员、服务过程和健康预警关联为可追溯的业务链。它是面向真实场景的全栈 MVP；现阶段使用合成演示数据，未进行真实社区试点，不将演示效果等同于实际运营成效。

| 用户 | 核心目标 | 产品支持 |
|---|---|---|
| 老人 / 家属 | 预约、查看进度与费用 | 本人预约、工单、账单与评价 |
| 护理员 | 明确任务并记录执行 | 接单、签到、服务项、照片、签退 |
| 网格员 | 调度与风险处置 | 受理、候选推荐、派单、预警闭环 |
| 机构 / 街道 | 质量与监管 | 统计、投诉、结算复核及审计 |

作品定位为垂直社区服务平台。应用中的推荐是加权算法，预警是可配置规则；AI主要参与开发、排错和材料整理，当前应用没有调用大模型生成医疗建议。

# 02 / 一笔服务的数据闭环

主流程从老人或家属提交预约开始。网格员受理后转入待派单，系统先过滤不满足条件的护理员，再排序推荐。网格员做出选择，生成带价格快照的工单。

护理员接单、定位签到、逐项完成服务、上传照片并签退。体征数据进入健康监测，匹配启用规则后生成预警。网格员响应并记录措施与结论，保留响应和处置时间。

| 阶段 | 关键记录 | 需要守住的约束 |
|---|---|---|
| 预约 | 时间、项目、老人、周期 | 数据权限、时间冲突与能力适配 |
| 派单 | 候选、原因、护理员 | 技能、半径、负荷、时段 |
| 执行 | 定位、照片、项目、小结 | 状态、本人任务及上传限制 |
| 健康 | 指标、规则、预警、处置 | 阈值、冷却、状态闭环 |
| 质量 / 结算 | 评价、投诉、金额快照 | 账单可见范围、累计退费上限 |

每个角色看到的导航与数据范围不同。服务闭环是主要演示内容，结算、审计与备份作为工程补充，不在有限演示时间内逐页堆叠全部模块。

# 03 / 架构与意图约束

后端采用 FastAPI 与 SQLAlchemy 2.0；前端采用 Jinja2、Bootstrap 与本地 ECharts；SQLite为本轮验证数据库。保留现有技术栈降低改写范围，也使评审环境无需额外前端构建服务。

| 层次 | 代码位置 | 职责 |
|---|---|---|
| 页面与交互 | app/templates、app/static | 角色导航、表单、图表、操作反馈 |
| API与认证依赖 | app/api/v1、app/core/deps.py | 请求校验、认证、权限和数据范围 |
| 服务 | app/services | 状态、事务、业务约束与审计 |
| 算法 | app/algorithms | 派单、规则判定、补贴计算纯逻辑 |
| 模型与存储 | app/models、app/db | 实体关系、会话与持久化 |
| 任务 | app/tasks | 调度入口和任务函数 |

对AI的架构约束是复用现有分层：不在模板里复制金额算法，不让接口通过ID绕过数据权限，不将状态流转散写成任意字符串更新。算法层保持可独立测试；服务层协调跨实体操作。

HTTP请求经过认证与权限依赖进入服务。服务访问数据库、执行规则、写业务记录及审计，最终返回统一响应。代码生成的结果需要人工理解和验证，不能以“AI已经生成”为验收依据。

# 04 / 数据与状态设计

核心实体包含组织、用户、老人、护理员、服务项目、价格版本、预约、工单、健康指标、预警、评价、投诉和账单。种子幂等检查涉及40张表，该数量来自现有真实验收记录。

预约关联老人和服务项目；派单生成工单并固定单价、价格版本及金额快照。后续调价不应重算历史工单。工单执行记录与照片、评价、账单明细关联；健康指标和预警通过老人档案连接。

五类单据采用集中式状态机：预约、工单、预警、投诉、账单。非法流转返回冲突；终态不通过便捷分支重新打开。取消或爽约同步释放关联工单占用的时段。

| 单据 | 主线状态 | 设计重点 |
|---|---|---|
| 预约 | 待受理→已受理→待派单→已派单→服务中→完成 | 取消、爽约和重排须有合法入口 |
| 工单 | 待接单→已接单→服务中→待评价→完成 | 执行人、定位、服务项和异常留痕 |
| 预警 | 待处置→已处置 / 误报 / 已转诊 | 响应记录与闭环措施 |
| 账单 | 草稿→待复核→已确认→已缴费 / 已红冲 | 差异复核与退费不能突破原余额 |

审计采用前向关联的哈希链，便于检测变化；不能将该机制宣称为具备外部可信锚的绝对不可篡改存证。

# 05 / 可解释派单与超时处理

派单采用“先过滤，再评分”。技能缺失、超出服务半径、达到日单量上限或时段冲突的人员不进入候选。手工派单和改派执行同样的约束，避免界面手选成为绕过规则的入口。

四项归一化因子为技能S、距离D、负荷L、评分R，默认权重依次为0.4、0.3、0.2、0.1。最终得分是四项加权和；重点关注人员再乘降权系数0.8。

负荷按服务发生日期统计；评分取最近30天实际评价，缺失时使用默认值。非法、负数或非有限权重回退到默认配置。候选返回原始因子、权重、加权贡献和降权信息。

30分钟未接单的起点为工单派出时刻。系统尝试尚未尝试、当前仍符合条件的候选；没有候选时写通知并提示人工协调，不把提示等同于独立人工受理队列。

历史代码可追溯到证据源L98、L106、L115；失败与回归记录见L185、L217、L248、L496。当前候选界面的权重/贡献展示由本轮浏览器分支继续核对。原始行号通过AI协同索引定位。

# 06 / 健康规则与服务留痕

健康指标通过服务录入或批量上报进入系统。规则支持单点阈值、连续异常和静默超时；按规则分为蓝、黄、红等级，同老人同规则有冷却去重。

红色预警保留通知和升级记录。网格员确认响应，再选择已处置、误报或转诊，并记录措施与说明。静默检测与超时升级有任务函数，但调度器实际到点触发尚未完整验收。

| 能力 | 当前实现 | 演示边界 |
|---|---|---|
| 可穿戴数据 | 模拟脚本通过正式接口上报 | 无真实硬件接入证明 |
| 短信 | 通知及模拟网关日志 | 无运营商真实送达证明 |
| 健康趋势 | 指标聚合与ECharts | 规则提示不作为医疗诊断 |
| 上门定位 | 坐标距离与超距原因 | 未接入地址地理编码 |
| 照片 | 数量、体积、像素检查与压缩 | 访问绑定工单范围，去除EXIF |

服务执行阶段同时保留时间、服务项和异常。定位偏差、时长偏差需要留痕；本轮自动浏览器验证与现有服务测试共同提供证据，不能据此推断真实设备、真实地址与生产网络均已验证。

# 07 / 权限、隐私与金额正确性

系统区分角色权限与数据范围：本人、网格、机构、街道。未绑定或缺少范围的账号默认不获得广泛可见性；具有操作权限仍需检查被操作记录是否在本人范围内。

预约、工单、投诉、回访、照片和账单均应受范围约束。合并账单在个人视角仅展示可见老人明细与相应汇总，避免总额和导出泄露其他家庭的信息。

身份证、电话和地址使用加密存储，检索使用摘要，列表默认脱敏。查看明文需要带理由的短期二次授权，并记录审计。演示材料应只使用合成数据。

结算使用Decimal与金额快照。退费只以正数原明细作为来源，逐次扣除已退金额，限制各付款方剩余额度；末次精确退尽分币余额。部分退费后不能再用整单红冲重复退还。

CSV/XLSX对可能成为公式的文本前缀做转义，金额保持数值类型。照片原图进行大小、像素和元数据处理，预览需验证工单访问范围。

仓库历史仍含已跟踪的SQLite旁文件与依赖缓存；当前无远程仓库。本次交付使用白名单源码包及独立历史证据，不将现有目录未经审查直接公开。

# 08 / AI意图控制与上下文管理

参赛人的职责是确定问题与约束、检查行为是否符合业务，并决定是否接受AI结果。AI承担读码、方案、补丁、验证与资料整理。本轮用户明确要求环境确认后使用多个subagent并行完成计划。

每次任务提供目标、当前实现、允许修改的范围、不可破坏的规则、验证方法及交付证据。复杂问题先定位到有限文件，避免模型在无约束范围内重写系统。

本轮将工作拆为快速复现、浏览器质量、真实证据三个并行分支，主代理负责PDF、视频和集成。各分支分配独占文件，减少共享工作区覆盖；跨分支发现通过消息传递，再由主代理整合。

| 控制环节 | 实际方法 | 验收依据 |
|---|---|---|
| 范围 | 保留技术栈，明确独占文件 | 文件变更与范围核对 |
| 上下文 | 计划、现有实现、错误输出 | 问题能定位到具体模块 |
| 约束 | 不改现有演示库、不伪造历史 | 隔离路径、原始证据及哈希 |
| 反馈 | 传递真实失败、工具与路径 | 重跑对应场景，保留失败结果 |
| 集成 | 汇总检查与材料一致性 | 自动化报告与人工审阅 |

这里总结的是可观察的协同方法，不把建议模板冒充已发生的用户Prompt。相同Prompt在不同模型中不保证生成相同代码；版本和补丁用于确定代码状态。

# 09 / 真实迭代案例：周期预约

已有优化轮发现，原周期预约仅保存weekly标识，并未实际生成四周预约。这会使用户以为已预约多周，而系统只有一条记录。

修复意图为：生成连续4周；每次都校验时间、权限与服务适配；任意一周冲突时整组回滚；普通单次预约保持兼容。实现复用预约服务，以事务包裹整组创建，接口返回次数与各次结果。

| 证据位置 | 记录含义 |
|---|---|
| 来源L165 | 读取预约页面、服务与现状 |
| 来源L173 | 四周循环、嵌套事务、选项和接口调整 |
| 来源L248 | 新增相应回归用例 |
| 来源L272 / L277 | 失败记录与测试数据修正 |
| 来源L496 | 最终全量测试结果 |

本案例体现将用户可观察行为变为事务约束，并通过冲突负例验证。不能只检查返回数量等于4；还要检查第2至第4周冲突时数据库没有留下部分预约。

证据限制：该案例来自一条整体优化请求中的自主拆解，未取得单独的人类追问和修复引导，不将其包装成独立完整人类Prompt链。早期用户中文在本地来源中存在编码损坏，导出保持原状并说明。

# 10 / 真实迭代案例：派单与权限

派单问题包含错误计时起点、服务日负荷使用错误，以及手工派单绕过限制。AI读码后修订算法与服务，保留旧语义用例失败，再调整用例预期并增加29分59秒/30分钟等边界。

# 11 / 本轮新迭代：运行环境与复现

应用已有虚拟环境可用，但系统默认python指向失效旧解释器，直接新建环境失败。主代理将真实错误传给复现分支，改用已验证的基础Python路径，并在启动脚本中支持显式BasePython参数。

复现分支进一步发现：PowerShell的ErrorActionPreference不能可靠拦截原生命令失败；已有但不完整的虚拟环境会被直接使用；数据库判断固定为data/app.db而忽略配置。

修复加入原生命令退出码检查、依赖导入检查、端口预检、环境模板初始化、基于配置的SQLite路径判断，以及Port/NoReload参数。已有.env不覆盖，已有数据库不重置。

新目录验证从白名单源码复制开始，初始没有venv、数据库和.env。使用预装Python 3.12.14、Windows、清华PyPI镜像，初始pip HTTP/wheel缓存为0字节。完成安装、初始化及6类角色13页面访问耗时85.563秒，总含收尾85.656秒。

前端修复稳定后又执行最终应用副本验证，耗时93.391秒至全部登录成功，缓存仍为0字节、通过网络下载；97个应用、依赖与启动配置文件SHA-256与当前一致。最终报告为reports/chuanzhi-reproduction-final.json，保留首次结果作为独立证据。

这是本机实测结果，不含Python预安装与远程clone；不能把它当作所有网络和机器上的保证。机器可读证据见reports/chuanzhi-reproduction.json，分阶段原始日志与源码哈希在对应runs目录。

# 12 / 本轮新迭代：交互反馈

浏览器分支发现多个页面调用App.toast，而公共对象未导出toast函数。业务请求成功后仍可能抛TypeError，导致跳转或刷新中断。仅做HTTP状态检查不会发现这一问题。

基线在真实Edge浏览器中确认App.toast为undefined。修复将其导出，并检查Bootstrap默认toast隐藏样式；同时改善通用动作加载与重复点击处理，以及预约成功跳转前的禁用状态。

派单候选展示核对实际权重、加权贡献与降权信息；按钮与弹窗关闭按钮的点击区域按适老化需求检查。三档字号为18、21、24px，浏览器验证覆盖桌面与390px宽度。

本轮浏览器运行使用隔离数据库和上传目录，禁用调度任务，避免修改用户现有演示数据。报告明确区分自动化浏览器验证和人工使用体验，不将脚本通过描述为完成真实老年用户可用性研究。

最终补充运行共28项检查通过，含非默认候选权重与处置500失败保留输入。截图与最终检查结果由docs/chuanzhi/浏览器验收.md及reports/chuanzhi-browser目录提供；基线失败保留作为排错证据。
