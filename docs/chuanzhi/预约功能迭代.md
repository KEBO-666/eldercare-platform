# 预约功能真实迭代与操作验收

日期：2026年11月12日。用户本轮原始要求：“在预约功能中完善 时间冲突、周期预约、取消后的时段释放”。本文为实际实施摘要，不是完整聊天导出，也不冒充用户尚未进行的试用反馈。

## 修改后的行为

1. **时间冲突**：继续执行同一老人预约或工单开始时间前后两小时（包含恰好两小时）的限制，同时检查实际服务区间重叠。预约按项目标准时长，工单优先使用派单时保存的结束时间；缺少结束时间时回退到项目时长。两小时规则以外、服务区间刚好首尾相接时允许。取消、爽约预约及已取消工单不继续占位。
2. **周期预约**：单次或连续四周同一时间；提交前可查看每次日期与预计结束时间，并点击“检查时段”。预检只读、不创建或锁定预约，真正提交重新检查。任一次冲突均不创建四次预约；错误指出第几次、冲突单号和时段。四次创建后独立受理、派单和取消。
3. **取消释放**：取消预约同步取消关联工单，释放老人和护理员时段，返回实际取消费用与释放工单数。预约、工单、费用、状态日志、审计整体成功或整体回滚。重复取消不能改写原原因与费用；遇到已服务等不允许取消的关联工单时整次操作失败。
4. **操作反馈**：取消失败保留原因、恢复按钮，处理过程中防重复操作；成功展示实际费用和释放数量。周期标签和取消费用保留在列表中；只取消本次，不影响其他周。修正“已经自动转人工”的误导文案，实际校验失败不会创建人工受理单。
5. **可选老人范围**：预约页面按角色范围提供老人；绑定老人直接查询，不受前300条列表限制。预检使用与创建一致的数据权限。

保持原有演示环境允许补录历史日期的约定；没有增加不兼容的“禁止过去日期”。日期溢出改为明确业务错误。没有新增数据表或改写真实演示数据库。

## 实际发现及旧版本复现

本轮基线为原本地提交`169b263e24b0ad5c311e92d8cd5c9e778241e2ae`，以白名单导出至隔离目录，使用新回归测试验证旧应用，复用已知依赖环境，不称为冷安装。

六个选中用例在旧版本中五个失败、一个通过：

- 四小时服务，开始时间相隔三小时仍被允许，两个方向均漏检。
- 已取消预约再次取消虽然报错，但原因字段被改写，调用者继续提交可保存错误修改。
- 同一预约多个关联工单中一个不能取消时，取消/爽约失败仍残留预约终态；两个动作分别复现。
- 两个服务区间首尾相接且超过两小时限制的用例正常通过，继续保留。

原始结果：`reports/appointment-iteration-baseline/20261112-183524/result.json`、`pytest.log`、`junit.xml`、`source-sha256.json`。失败输出包含真实断言，未修改旧版本来制造缺陷。

## 参赛人亲自试用步骤

1. 启动应用，使用老人账号进入“提交预约”，选择服务、上门时间和“每周固定（连续4周）”。核对四个日期，点击“检查时段”，确认列表尚未新增记录。
2. 提交后在预约列表核对四条“每周预约”。再对相同老人、相同时段提交，检查冲突提示；四周申请若某一周冲突，四条均不新增。
3. 用网格员受理其中一次、转待派单，并为其派单。取消这一次，核对实际费用、释放工单数量，以及其余三次仍然存在。
4. 给同一老人重新申请刚取消的时段，再由网格员派给原护理员，核对时段已释放。
5. 如果遇到任何不符合预期的结果，记录账号角色、操作、预期和实际表现，在当前对话中反馈；后续据真实反馈继续修复，不能把AI自动验收描述为本人试用。
