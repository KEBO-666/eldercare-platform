# 健康预警权限、状态与追溯说明

本说明对应 2026-11-12 的源码与本轮验证，补充健康指标录入、人工异常上报、响应处置、转诊随访和审计查询的实际行为。测试结果见汇总报告 [`reports/health-alert-assurance-summary.json`](../../submission/verification/health-alert-assurance/summary.json)。

## 1. 权限与数据范围

权限定义以 `app/core/permissions.py` 为准，HTTP 接口通过 `require` 检查动作权限，再检查对象是否属于当前用户的数据范围。默认六角色在本模块的授权如下；自定义角色可独立增减权限，不能根据角色名称推测权限。

| 默认角色 | 健康读取 | 指标/设备写入、人工异常上报 | 预警读取 | 响应/处置/随访 | 维护规则/手动扫描 | 审计读取 |
|---|---|---|---|---|---|---|
| 老人/家属 | 无 | 无 | 有 | 无 | 无 | 无 |
| 护理员 | 有 | 有 | 有 | 无 | 无 | 无 |
| 网格员 | 有 | 无 | 有 | 有 | 无 | 无 |
| 机构管理员 | 有 | 无 | 有 | 无 | 无 | 无 |
| 街道监管员 | 有 | 无 | 有 | 有 | 无 | 有 |
| 超级管理员 | 有 | 有 | 有 | 有 | 有 | 有 |

对应权限分别为 `health:read`、`health:write`、`alert:read`、`alert:handle`、`alert:rule`、`admin:audit`。写入或处置权限不自动授予读取、规则维护或审计权限。人工异常上报使用 `health:write`，与维护规则分开。审计详情包含完整措施和备注，只能向有审计权限的账号提供。

仅有 `health:read` 的账号可读范围内健康记录，但健康页、首页不查询或展示预警摘要、预警数量和预警规则区块，也不提供相关预警入口。导航的健康、预警和审计入口分别按实际权限过滤；预警详情的健康监测、关联审计链接也独立受控。直接请求页面或 API 仍会再次鉴权，隐藏按钮不是权限边界。

| 数据范围 | 本模块实际限制 |
|---|---|
| 老人/家属 SELF | 绑定账号的老人档案及其预警 |
| 护理员 SELF | 本人护理员工单关联的老人及其指标、设备、预警；不能扩展到同网格其他老人 |
| GRID | 老人 `grid_org_id` 属于用户网格；预警等无网格字段的实体通过老人关系收窄 |
| ORG | 老人 `community_org_id` 属于用户机构/社区 |
| STREET / 超级管理员 | 沿用项目既有“不限制”约定，不新增多街道租户隔离 |

无机构、无绑定老人或无护理服务关系时返回空范围。列表、统计、详情、健康趋势、设备列表和页面采用相同范围；请求指定别人的编号不能扩大范围。越权健康写入拒绝保存，越权预警详情和处置不返回对象内容；批量指标保留原条目索引并逐条返回拒绝原因。未认证、无效令牌和停用账号不能读取或写入模块内容。

## 2. 五阶段与最终闭环

底层 `status` 保留 `pending/resolved/false_alarm/referred` 兼容字段，页面和统计根据状态与流水派生五阶段生命周期。

| `lifecycle_status` | 业务含义 | 可继续操作 |
|---|---|---|
| `unacknowledged` | 待响应 | 确认响应、记录进展、提交处置 |
| `responded` | 已首次响应，待处置结论 | 记录进展、提交处置 |
| `handling` | 已记录处置进展 | 继续记录进展、提交处置 |
| `awaiting_followup` | 已登记转诊，尚未获得最终随访结果 | 记录随访；确认实际结果后闭环 |
| `closed` | 已处置、误报核实完成或转诊随访完成 | 读取历史，不能再响应或追加处置/随访 |

确认响应只记录首次响应，不会完成处置，也不会停止未闭环事项的超时追踪。首次响应重复提交返回原结果和 `already_acknowledged`，不会新增响应流水、改写首次时间或重复写响应审计。记录进展、直接处置会自动补记首次响应。

提交 `resolution_type=referred` 后，`resolved_at` 表示转诊登记时刻；它不是最终闭环时刻。`follow-up` 的 `close=false` 记录随访进展，`close=true` 才记录 `followup_close` 并完成最终闭环。最终判断使用 `closed/closed_at`，耗时使用 `closure_seconds`。兼容统计字段 `closed` 仍包含“已登记处置”的转诊，界面使用 `lifecycle_open/lifecycle_closed/referral_followup_pending`，不能拿旧统计字段宣称转诊已经闭环。

## 3. 状态复检、时间与失败处理

处置、响应、进展与随访在写入前，对当前用户范围内的预警执行不改变业务列的 `UPDATE`，先获得写锁，然后以 `FOR UPDATE` 查询并使用 `populate_existing=True` 刷新 Session 中可能过期的状态。SQLite 不执行行级 `SELECT FOR UPDATE`，因此前置写操作承担串行写入的作用。已读到旧状态的 Session 必须按数据库最新状态重新判断，不能重新打开已闭环记录，不能在别人完成随访后继续追加随访。自动升级也在更新前复检未闭环、截止时间、尚未升级等条件。

直接处置先补记首次响应，再取得处置时刻，确保首次响应不晚于处置与闭环。新响应流水先 flush，再生成审计后值，保留真实微秒时间；整数 `response_seconds` 是耗时，不用于重建新记录的精确时间。历史仅有耗时的记录仍保留兼容推导。带时区测量时间转换成 UTC+08:00 后存为无时区时间，未带时区输入保持项目本地时间；部署主机约定使用北京时间。

响应、处置、进展、随访、人工异常上报和扫描的数据库状态、动作流水、通知与对应审计在事务中整体成功或回滚。非法状态、无效参数、越权或事务内审计失败不能留下部分处置结果。扫描处理尚未最终闭环的待处置及转诊待随访预警；已经最终闭环的记录不再升级。

健康指标采用两个保存阶段：指标与 `create` 审计先独立提交，预警评估及其副作用再单独提交。返回的 `alert_evaluation.status` 明确区分 `created/no_match/cooldown/no_rules/error`；冷却反馈可关联 `existing_alert_id`。评估失败回滚部分预警、通知和相关成功审计，保留已经保存的指标，另记录评估错误；前端提示联系管理员核实，不应重复录入指标。批量中失败的单条不回滚前后已成功条目。

请求超时、网络中断或返回内容无法确认时，浏览器保留填写内容并锁定继续提交，提示先核对服务器记录；详情可刷新取得最新状态。不能把“未收到确认”当作“服务器未处理”。

## 4. 从业务记录定位审计

| 实体 / 动作 | 记录内容 |
|---|---|
| `health_metric / create` | 保存的指标、来源、关联编号、测量时间与记录人；HTTP 请求来源 |
| `health_metric / evaluate` | 本次评估状态、评估/命中数量、冷却结果与新预警编号；错误结果不暴露内部异常详情 |
| `alert / create` | 新预警、来源指标/人工报告、初始生命周期与通知关联 |
| `alert / ack` | 首次响应前后状态、精确响应时间；重复确认不新增 |
| `alert / handle` | 处置前后状态、措施、完整补充备注、执行人、处置与最终闭环字段 |
| `alert / progress、report、followup、followup_close` | 对应追踪前后状态、记录原文与操作者；最终随访动作单独留痕 |
| `alert / escalate` | 具体预警升级前后状态、升级时刻；执行人为系统 |
| `alert_scan / scan` | 扫描结果与 `trigger=manual/scheduled`；手动扫描记录请求用户，定时扫描记录系统来源 |

`AlertAction` 面向全过程业务追踪；受保护的 `AuditLog.before_json/after_json` 保留状态前后值和完整处置文本。处置流水的简要内容可能限长，核对完整措施与备注应读取受保护审计及预警字段。

有 `admin:audit` 权限时，预警详情提供“关联审计记录”，进入 `/admin/audit?entity_type=alert&entity_id=<预警编号>`。API 对应 `/api/v1/admin/audit-logs?entity_type=alert&entity_id=<预警编号>`。类型与编号必须联合使用，避免不同实体恰好同号而混入其他记录。指标审计使用 `entity_type=health_metric` 与指标编号；扫描汇总另查 `entity_type=alert_scan`。

审计页面以可折叠、可换行的中文 JSON 展示前后值，使用 HTML 转义，处置文字中的 `<script>` 等内容只能作为文字显示。API、页面、哈希链校验均检查 `admin:audit`；普通处置员不能因能够处理预警而读取受保护审计。

审计写入通过 `prev_hash` 关联前一条，并对所覆盖的业务字段计算 SHA-256；修改受保护措施等内容会使校验失败。`/api/v1/admin/audit/verify` 返回 `valid/checked/broken_id`，校验有数量上限，应查看实际 `checked`。哈希链提供所覆盖内容与连接关系的篡改检测，不是外部签名、独立不可变存储或对所有数据库列的完整性保证。

## 5. 验证与交付边界

本轮新增四类测试文件，并继续运行既有健康上报、预警生命周期、页面和前端回归：

| 测试文件 | 主要验证 |
|---|---|
| `tests/integration/test_health_alert_permissions.py` | 六角色动作矩阵、独立权限、首页与导航隔离、各范围列表/统计/详情/页面一致、匿名/停用及越权无副作用 |
| `tests/integration/test_alert_transition_matrix.py` | 五类存储/终态样本与七类操作矩阵、非法参数、首次响应保持、多个 Session 的旧状态复检 |
| `tests/integration/test_alert_traceability.py` | 指标保存与评估、人工报告、处置进展、完整措施、手动/定时扫描、实体过滤、权限及哈希篡改检测 |
| `tests/integration/test_alert_assurance_pages.py` | 下述五项页面、时间及自动升级验证 |

最后一个文件包含五项：审计按实体编号精确过滤且中文可读/HTML 转义；审计入口与页面权限；首次响应审计保留精确微秒时刻；自动升级仅写一次具体预警状态审计并区分扫描来源；直接处置不早于自动首次响应。最终通过情况、全量检查、前端及浏览器证据索引以汇总报告为准：[`reports/health-alert-assurance-summary.json`](../../submission/verification/health-alert-assurance/summary.json)。

API 测试使用新建合成内存库；多个 Session 测试也在隔离测试引擎上执行。浏览器验收使用单独生成的演示库及临时目录，不改现有真实数据库。短信为模拟日志，并未接入真实短信或急救调度；模拟文件不参与数据库回滚。

SQLite 写锁、状态复检和重复响应保护解决本轮验证的写入与旧 Session 问题，不代表已验证跨进程、跨服务或外部通知的 exactly-once（恰好一次）语义。已有 PDF 和演示视频属于之前版本快照，不能作为本轮新增权限、锁与审计行为的最新证据；本轮以当前源码、测试和汇总报告为准。
