# 健康异常上报与预警闭环追踪

2026年11月12日，用户要求完善健康预警中的“异常上报、响应、处置、闭环追踪”。本轮保留原有数据表和旧API字段，增加实际可操作的上报与跟踪流程。

## 操作入口

1. 使用超级管理员或有健康录入权限的护理员登录，进入老人“健康监测”页。可录入指标；跌倒、身体不适等情况可填写“人工异常上报”。摘要、现场情况和级别随预警保存。
2. 指标保存后常驻展示检测结果：新预警、未命中、冷却去重、没有适用规则、评估失败。新预警和冷却关联预警均提供追踪入口；没有新预警不能理解为健康正常。
3. 网格员或街道等有处置权限的账号进入预警看板，点击“响应 / 处置”。确认响应会记录首次时间；重复确认保留原时间，不重复追加流水。
4. 实际处置中可多次记录进展。提交结论时页面要求具体措施；误报需要记录核实依据。已处置和误报完成本次闭环。
5. 转诊登记进入“转诊待随访”，继续记录接收与随访结果；有实际结果后点击“确认随访完成并闭环”。详情保留来源、触发、通知、首次响应、处置、升级、随访和最终闭环时间及操作人。

## 状态与计数

| 实际阶段 | 判断依据 | 可执行操作 |
|---|---|---|
| 待响应 | pending，尚无首次响应 | 响应、进展、处置 |
| 已响应 | pending，已响应且无进展 | 进展、处置 |
| 处置中 | pending，已有进展 | 追加进展、处置 |
| 转诊待随访 | referred，尚无最终随访闭环 | 随访进展、最终闭环 |
| 已闭环 | resolved、false_alarm，或referred且有followup_close | 查看追踪 |

页面与统计使用同一派生生命周期。保留旧`status=referred/resolved_at/handling_seconds`，用于兼容转诊登记；最终闭环以`closed/closed_at/closure_seconds`为准。看板不会把尚未完成随访的转诊计为闭环。响应和进展不会停止未闭环超时追踪；超过截止的待随访转诊同样可升级，升级只记录一次。

## 异常处理

- 空记录、超出长度、非有限或越界指标、非法来源和时间会被拒绝。设备与工单必须属于同一老人；所有写入同时受权限和数据范围约束。
- 批量上报逐条校验和保存。返回原始条目索引、成功结果和失败原因；一条非法时间或数据库失败不阻断其余条目，错误反馈不暴露SQL参数。
- 指标先独立保存，预警评估失败会回滚部分预警写入，并明确提示指标已保存、请联系管理员核实，不要重复录入。
- 网络中断、超时、500或不完整成功响应不会被当成成功，也不会冒称操作没有发生。页面保留输入、锁定重复提交，提示先核对记录；追踪页取得最新服务器快照后才开放继续操作。
- 记录响应、处置、进展、人工上报、随访和扫描时，数据库写入与审计失败整体回滚。该验证不等于多进程并发幂等或真实短信网关送达保证。

## 规则与运行边界

页面展示当前启用规则，移除原先“48小时”与“3天”的冲突提示。内置静默扫描执行启用的`SILENCE`规则，其他静默编码仅配置留存；停用后停止生成静默警，但继续升级已有未闭环事项。静默事项转诊未闭环时不会重复生成。

带时区的测量时间转换为UTC+8本地无时区时间，缺省时间沿用项目本地时钟，演示部署应使用北京时间。短信为模拟日志，站内通知用于演示留痕。自动扫描依赖调度器运行；API也提供`POST /api/v1/alerts/scan`供有规则权限的账号触发。
