## 一、参赛目标与作品定位

### 1.1 作品定位

建议作品名称为《颐邻——社区智慧养老服务与健康监测平台》。面向社区居家养老中的服务预约分散、护理人员调度困难、服务过程缺少留痕、健康异常处置不及时等问题，提供多角色协作的 Web 应用。

核心产品故事为：

> 老人或家属提出服务需求，网格员受理并选择推荐护理员，护理员完成上门服务并录入健康指标，异常指标触发预警，网格员记录处置结果，服务费用与评价可追溯。

作品可按“垂直社区全栈 MVP”定位申报。规则中部分推荐方向的名称与说明不完全对应，申报时以真实业务场景和完整数据流说明价值，不宣称实现数字孪生、具身智能或多智能体。

1. 以真实的 AI 辅助开发过程为主线，展示选手如何定义问题、约束架构、检查结果和引导修复。
2. 保留 FastAPI、SQLAlchemy、Jinja2、Bootstrap 和 ECharts 技术栈，优先交付稳定的核心流程。

### 5.2 上下文与Prompt模板

每次迭代提供最小必要上下文：相关业务规则、当前文件、接口契约、已知错误和验证命令。优先让AI说明影响范围，再实现与检查；涉及权限、金额和状态机时明确不可绕过的约束。

以下模板仅用于未来实际任务，不作为已发生对话的证明：

```text
目标：解决一个可观察到的业务问题，写出触发条件与期望结果。
现状：说明相关模块、当前行为、已有测试或错误信息。
约束：保持接口兼容；按角色校验数据范围；复用现有事务与状态机。
边界：明确空数据、冲突、重复提交、失败回滚等与本次任务有关的情况。
执行：先说明定位与影响，再修改必要文件；对关键风险补充有意义的验证。
交付：列出改动、实际验证结果、尚未验证事项，并保留相关文件路径。
```
